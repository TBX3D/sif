# sif v2.2 / v3 — major-update roadmap (design)

*Local planning artifact. "v2.2" and "v3" are internal cosmetic labels like "v2"
and "v2.1" before them — they must NEVER appear in commits, PRs, or code. All work
stays in per-lane worktrees, committed locally, nothing pushed to GitHub; PR
splitting is a deliberately-deferred later pass.*

## Context

sif (github.com/vmfunc/sif) has just completed a local "v2.1" continuation on top
of an "all-v2-PRs-accepted" base:
- `v2.1-base` = the 8 v2 pillar branches merged (dns #307, tcp #308, sarif-sev
  #312, json+confidence #313, framework-multi #314, global-context #315, embed
  #316, chaining #317) on the exposure firehose. Green.
- `feat/richer-matchers` — case-insensitive / encoding / `type: range` matchers,
  threaded through the shared word/regex helpers so HTTP+DNS+TCP inherit them.
- `feat/cross-target-concurrency` — `-concurrency N` worker pool, index-ordered
  merge, locking console sink, race-clean.
- `v2.1` = both integrated, clean, gauntlet-green.

All four preserved as `snapshot/*-20260707` tags before this roadmap began.

The next major update spans three axes the user wants together: **engine power**,
**operational maturity**, and **detection depth**. Chosen structure (Approach C,
flagship-first): make the **YAML-dialect merge the v2.2 flagship**, orbit it with
the dependency-free consolidation wins, and gate the high-risk engine leap behind
it as v3.

## Version framing

- **v2.2 — "the unification release."** Flagship: collapse sif's two user-facing
  YAML systems into one dir/format. Around it: the engine leftovers that feed the
  flagship, the detection-depth content that has no dependency on it, and the one
  cheap operational win (config file + profiles).
- **v3 — "the engine leap."** The high-ceiling work that *requires* the unified
  schema as substrate (expression-DSL matchers, fuzzing/payload-sets) plus the
  CLI-breaking operational items (subcommands, resume/checkpoint), isolated to the
  v3 boundary so the breaking change lands once.

## Flagship — unify the two YAML dialects (v2.2)

sif today has TWO user-YAML systems: framework custom-signatures
(`internal/scan/frameworks/custom.go`, `~/.config/sif/signatures`) and modules
(`~/.config/sif/modules`). The flagship collapses them onto one dir/one format.

Grounded in the existing `spike/unify-cutover` cutover plan
(`UNIFY-CUTOVER-PLAN.md`, `PHASE3-EXPLORATION.md`), which frames the problem with
the epistemology→architecture model: split into CLOSED subproblems (an oracle
exists → prove them) and one OPEN residual (a human call). Two gated phases:

### Phase A — CLOSED proofs (unconditional, build first, zero blast radius)

Pure upside, reversible (tests only), and they convert "is the merge safe?" from a
claim into a checkable fact:

- **C2 differential-equivalence test:** assert
  `scoreFingerprint(sigs, body, headers) == BaseDetector.MatchSignatures(body,
  headers)` on the shared domain (all weights > 0) over randomized inputs; pin the
  one known divergence at `weight == 0` (MatchSignatures counts 0, scoreFingerprint
  maps to 1 — outside custom's validated domain since `custom.go` rejects
  `weight <= 0` at load). Falsify, don't assert.
- **C3 delta-regression tests:** pin the three behavioural deltas — `>` vs `>=` at
  the detection threshold, weight `>0` vs `≥0→1`, single-winner vs per-finding
  arbitration.
- **C4 trap test:** a non-root / confidence fingerprint is NOT silently registered
  and run as a framework detector (the step-5 trap where `path`/`confidence` are
  ignored by the framework engine).
- **C5 back-compat test:** legacy `signatures/*.yaml` still loads unchanged.

The `spike/fingerprint-type` branch (`type: fingerprint` module) is the concrete
bridge primitive these proofs validate.

### Phase B — the bridge (built locally now, behind a reversible seam)

Point both loaders at one dir/format. Reversibility baked in:
- back-compat read of legacy `~/.config/sif/signatures/` + a deprecation log (O2),
- root-path guard + confidence-wrap so "same file, two engines" can't silently
  diverge (O3 / C4).

A wrong call costs a rollback, not a migration.

### The O1 gate (open residual)

Whether to *commit* the merge upstream is a product decision — the maintainer's
call, not a code call. For this local roadmap the user has answered "yes, build
it," and because a local commit is not the irreversible act (the PR/merge is), we
build Phase B locally now and carry the C2–C5 proofs into the eventual PR
conversation. **O1 is a PR-time gate, not a build-time gate.**

## v2.2 orbiting axes (parallel lanes, no dependency on the flagship)

- **Engine leftovers (feed the flagship):** `spike/fingerprint-type` → real
  `type: fingerprint` module; the sigmoid-lift refactor (behavior-preserving,
  differential-tested). These converge into the bridge.
- **Detection depth:** favicon SSOT (`feat/favicon-fingerprint-module`, the
  deliberately-skipped v2 Pillar 1c, now unblocked); CVE enrichment
  (`fix/cve-bare-major-version` + references/versioning in `cve.go`); a
  detector-tuning FP/FN pass (via the detector-tuning skill).
- **Operational (one cheap win):** config file + named profiles — greenfield,
  feeds the whole flag surface from a file/profile. The rest of the ops axis
  defers to v3.

## v3 — the engine leap (gated on the unified schema)

- **Expression-DSL matchers** — a real matcher expression language; the unified
  schema is its precondition, so building it pre-merge would be wasted work.
- **Fuzzing / named payload-sets / sniper-batteringram** attack modes.
- **Subcommands** — user-facing CLI restructure; breaking, isolated to the v3
  boundary.
- **Resume / checkpoint** — long-scan durability; interacts with the v2.1
  cross-target concurrency.

## Execution model

- **Preserve first:** v2.1 branches tagged `snapshot/*-20260707` (done).
- **Worktrees:** per-lane off a fresh `v2.2-base` (created off `v2.1`), the v2.1
  pattern. opus-research → sonnet-impl pairs. Local scoped commits only, no push.
- **Dependency order:** flagship Phase A + engine-leftovers + fingerprint-type
  first (they converge into the bridge) → flagship Phase B → orbiting
  Detection/Ops lanes in parallel → v3 leap last.
- **Verification per lane:** `go build ./...`, `go vet ./...`,
  `go test -race -count=1 ./...`, `golangci-lint run ./...` (all green), plus an
  independent re-verify by the orchestrator. Env: `GO111MODULE=on
  GOTOOLCHAIN=local`; lint cache `GOLANGCI_LINT_CACHE=/tmp/claude-1000/...`.
- **House style:** lowercase scoped `type(scope): subject`, no em/en-dashes, no
  emoji, no AI/tooling trailers, minimal comments, verify-don't-assert,
  `Finding.Line()` output FROZEN.
- **Deferred to PR-time:** the O1 product decision, per-commit
  vmfunc-lint/style-review, PR splitting.

## Critical files / branches

- Flagship: `internal/scan/frameworks/custom.go`, `internal/modules/fingerprint.go`,
  `frameworks` scorer vs module scorer; spikes `spike/unify-cutover`,
  `spike/detectors-to-yaml`, `spike/fingerprint-type`.
- Detection: `internal/scan/favicon.go` + `feat/favicon-fingerprint-module`,

- Operational: greenfield config loader + `internal/config/config.go`.

## Non-goals (explicit)

- No `script`/code executor (new trust boundary; needs its own sandboxed RFC).
- No pushing to GitHub / opening PRs this round.
- No touching v2.1 branches (frozen + tagged).
- v3 items are NOT built in v2.2; they are sequenced, not started.

## Open questions carried forward

- Config-file format (toml vs yaml) and profile-precedence rules — settle at the

- Expression-DSL surface (how much of a language) — a v3 design question, not v2.2.
